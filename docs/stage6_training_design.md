# Stage 6: Training Experiment Design and Authorization Gate

Status: **design and data path only. No training has been run and none is
authorized yet.** This document records what Stage 6 would train, what the
data can and cannot teach, and the conditions that must hold before a
single optimizer step is taken.

## 1. Two behaviours, only one of which this data teaches

Regulus needs two different things from the model. They are not the same
problem and must not be reported as if one dataset covered both.

### Grounded extraction (this dataset teaches it)

Given the Stage 4 generation contract, the model must reproduce the
authoritative text of each requested provision, attribute it to the right
source number, keep provisions separate and in the order asked, and say
"not found in the available eCFR data" for a requested provision that has
no EXACT source. Every Stage 6 example is of this family:

```
extra.family        = "extractive_grounded"
extra.answer_style  = "verbatim_quote"
```

The target answer quotes the database row. That is strong, cheap and
verifiable supervision: the target is provably correct because it *is* the
source, and any deviation is detectable.

### Faithful paraphrase (this dataset does NOT teach it)

Explaining a provision in natural language while introducing no
unsupported substantive claim is a different skill. No example in this
dataset paraphrases anything, so:

* the dataset cannot teach faithful paraphrase;
* an improvement measured on it is not evidence of paraphrase quality;
* Stage 5's `semantic_faithfulness_results` remains the only place
  paraphrase behaviour is observed, and its method is heuristic.

Synthetic paraphrases are deliberately not generated. A paraphrase target
written by a model would need its faithfulness established by something
other than that model, and no such verifier exists in this project. Until
one does, paraphrase supervision is an open limitation, not a gap to be
filled with unverified text.

Practical consequence to watch for: training only on verbatim targets may
bias the model toward quoting. That is acceptable for a regulatory
assistant, but it must be *measured*, not assumed harmless. The Stage 6
comparison therefore tracks answer length, repair frequency and the
faithfulness block before and after training.

## 2. Categories and where they come from

| Category | Question shape | Answer |
|---|---|---|
| `multi_provision` | two or three provisions of one section | one block per provision, each quoting its row with its source number |
| `range_provision` | three or four consecutive provisions ("(b)(1) through (b)(4)") | one block per provision, in order |
| `partial_provision` | one provision that exists plus one proven absent | the present one quoted; the absent one reported as not found |

All three are generated by `src/regulus/stage6/generators.py` from live
`cfr_records` rows, grouped by section. The existing Stage 11/13/14
categories (direct_cfr, definitions, guidance, abstention, grounding
negatives) are kept; the composition is taken from the Stage 5 plan's
`recommended_composition` rather than chosen by hand.

## 3. Proving a provision is absent

An earlier draft picked the "missing" identifier as `max(existing) + offset`.
That infers absence from arithmetic and can name a provision that exists.
It was replaced before any data was generated.

`find_absent_child(section, parent)` now:

1. collects every paragraph path the snapshot holds for that section
   (`present_paragraph_paths`);
2. walks candidate child numbers past the highest present one;
3. returns the first candidate whose path is **absent from that complete
   set**, or `None` if every candidate tested is present.

Each `partial_provision` example records the proof:

```json
"missing_provision": {
  "requested_identifier": "21 CFR 820.10(b)(5)",
  "section": "820.10",
  "parent_paragraph": "(b)",
  "requested_child_number": 5,
  "absent_verified": true,
  "absent_check": "candidate paragraph_path compared against every live paragraph path of this section in the snapshot",
  "section_live_paragraph_count": 12,
  "parent_children_present": ["(b)(1)", "(b)(2)", "(b)(3)", "(b)(4)"],
  "snapshot_date": "2026-09-03"
}
```

`regulus.training.validate.check_stage6_examples` then re-verifies the claim
straight from the database, independently of what the generator believed: it
queries the live records for every section involved and fails the dataset if
any "absent" identifier is actually present, if its section has no live
records, or if the metadata is incomplete.

## 4. Training and inference use the same prompt

`TrainSettings.prompt_format` selects how an example is rendered:

* `legacy` — the Stage 6 RAG prompt, so Stages 12 to 14 still reproduce;
* `grounded` — the Stage 4 generation contract, which is what the pipeline
  sends at inference: `REQUESTED PROVISIONS`, tiered `SOURCE` blocks, the
  `ANSWER FORMAT` line.

Stage 6 uses `grounded`. `src/regulus/stage6/prompting.py` builds the
package from a training example, assigning each context item its tier by
identity (exact / structural / supporting, or the requested docket) using
the same rules the retrieval layer uses. Sibling paragraphs are supporting,
never exact or structural, and this is covered by tests.

## 5. Leakage prevention

Three separations, all checked by
`scripts/prepare_stage6_dataset.py` and written to
`data/training/datasets/separation_v6.json`:

1. **Question level** — an example whose question equals or nearly equals a
   benchmark question is dropped (existing `exclude_benchmark`, identifier-aware).
2. **Group level (new)** — an example whose split group (section, or
   "part N") is *named by any benchmark question* is dropped entirely
   (`quality.exclude_benchmark_groups: true`). If Stage 5 asks about
   21 CFR 820.10, nothing built from 820.10 may be trained on, so the
   evaluation cannot be measuring memorised text.
3. **Split level** — groups never cross train / validation / test, enforced
   at build time and re-checked on the written files.

`data/evaluation/datasets/stage5_v1.jsonl` is registered as a benchmark
alongside `baseline_v1` and the two retrieval sets, so all four are excluded
by both rules.

Adding the three Stage 6 categories and the fourth benchmark leaves the v1,
v2 and v3 datasets byte-identical: a category with no share is never
generated, and the group rule is an opt-in flag those configs do not set.

## 6. Checkpoint selection (designed, not yet run)

The Stage 12/13 lesson is explicit: validation loss fell while the task got
worse. Therefore:

* `keep_all_checkpoints` retains every checkpoint instead of the best two by
  loss;
* selection scores each checkpoint on a held-out, category-stratified
  validation subset with the *task* measures used in Stage 5 (validator
  status, every requested provision addressed, no unsupported content,
  refusal correctness), not on loss;
* a checkpoint is a candidate only if its task score is at least the base
  model's on the same examples;
* early stopping on `eval_loss` with patience 3 bounds the run; it never
  selects.

## 7. Authorization gate

Training may begin only when every line is true.

| # | Condition | Status |
|---|---|---|
| 1 | Stage 5 full 51-question baseline completed | see the Stage 5 report |
| 2 | All Stage 5 artifacts generated | see `artifacts/stage5_stage6/<run>/stage5/` |
| 3 | Failure analysis reviewed | `failure_analysis.json` |
| 4 | Stage 6 generators pass deterministic tests | `tests/test_stage6_generators.py` |
| 5 | Missing-provision generation verified against corpus data | generator proof + `check_stage6_examples` |
| 6 | Prompt contract tests pass | `tests/test_stage6_generators.py` |
| 7 | Benchmark leakage check passes | `separation_v6.json` |
| 8 | Dataset cardinalities reported by category | manifest + prepare script output |
| 9 | Train/validation/test group separation verified | `separation_v6.json` |
| 10 | Database untouched | read-only connection; no writes anywhere |
| 11 | Base model untouched | LoRA adapters only, written under their own directory |
| 12 | Training examples use the inference prompt contract | `prompt_format: grounded` |

Stage 5's `stage5_training_plan.json` carries a `proceed` flag, but that
flag is advisory. It is set only when the evidence layers are healthy and
enough model-side failures exist to be worth training on; it is never a
substitute for the human decision.

## 8. Known limitations

* Verbatim-only supervision; faithful paraphrase is untaught and unmeasured
  except heuristically.
* The Stage 5 evaluation set is 51 questions concentrated on a few parts, so
  every rate has a wide confidence interval.
* CPU training reaches roughly 100 optimizer steps overnight, so the
  achievable effect is small.
* Group-level benchmark exclusion removes the evaluation sections from
  training entirely, which is the right safety property but also removes
  the sections the evaluation understands best.
