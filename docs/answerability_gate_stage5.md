This does not mean hallucinations are solved. The gate prevents unsupported

support the request. Everything else is still generated by a 0.6B model and
checked afterwards by validation.

## A. Objective

Act on what Stage 4 could already detect. If the evidence cannot support an
answer, do not ask the model for one; instead return a safe, honest,
deterministic answer. When a repair fails, never show its output. Never present
unrelated retrieved text as "the verified text of the requested provision".
Keep every stage of the text inspectable: what the database supports, what the
model generated, what the validator accepted, and what the user received.

## C. Architecture before

```text
plan → retrieve → coverage → select → package
  ├─ grounding refused ............................ deterministic
  ├─ [structured mode only] out of scope .......... deterministic
  ├─ no requested provision found ................. deterministic
  ├─ nothing retrieved ............................ deterministic
  └─ else → Qwen → validate → repair
                         repair on failure: quote the first exact passages
                         ("verified text of the requested provision"), whatever was asked
                         a repair that still failed: shown anyway
```

## D. Architecture after

```text
plan → retrieve → coverage → select → package
  → ANSWERABILITY GATE (regulus/rag/answerability.py; deterministic, ~0.1 ms)
  ├─ blocked state ─→ SAFE FALLBACK BUILDER (regulus/rag/fallback.py) ─→ answer  (Qwen not called)
  └─ allowed  ─→ Qwen (unchanged prompt, settings, streaming) → validate
                   → repair_with_fallback:
                        repair (quotes a provision only when its text IS what was asked)
                        still ungrounded? → safe fallback (never shown as-is)
                   → PARTIALLY_ANSWERABLE: deterministic limitation sentence appended
```

Config: `RagConfig.answerability = "gate"` is the default; `"off"` restores
Stage 4 behaviour for measurement. The fingerprint is now version 3 (the
coverage section adds `answerability`).

The pipeline and the evaluation harness share one implementation of
`repair_with_fallback`.

Unchanged: the model, weights, prompt and system prompt, generation settings,
retrieval and ranking, the database, the benchmark files and keys, streaming,
CPU float32, and the MPS default. No new model call, LLM classifier or
network call was added.

## E. Answerability states

Every decision carries `state`, `reason`, `signals`, `confidence`
(PROVEN / PROBABLE / UNDETERMINED), `evidence_ids`, `blocking_conditions` and
`limitation`.

| State | Meaning | Action |
|---|---|---|
| ANSWERABLE | every requested provision has exact evidence; nothing checkable is missing | generate |
| PARTIALLY_ANSWERABLE | some provisions are found and some not; a requested value is missing from one part of a multi-part question; or a clause is out of scope | generate, then append a deterministic limitation |
| INSUFFICIENT_EVIDENCE | no requested provision is found; nothing is retrieved; or the whole question asks for a kind of value that no retrieved source contains | **block** |
| OUT_OF_SCOPE | a named non-U.S. framework with no U.S. reference (now in every answer-shape mode) | **block** |
| AMBIGUOUS | a provision is pointed at without being identified ("paragraph (b)", "this section") | **block**, ask the user to name it |
| WRONG_PROVISION | a citation lookup whose only named provision is the one being *referred to* ("…meeting part 803 criteria") | **block** |
| UNSUPPORTED_REQUEST | the user asks for a determination about a particular product or firm, or a prediction ("is my device compliant") | **block** |
| UNKNOWN | a general question; whether the sources answer it cannot be decided by rule | generate |

Counts on the diagnostic set: ANSWERABLE 46, INSUFFICIENT_EVIDENCE 14,
UNKNOWN 14, PARTIALLY_ANSWERABLE 3, OUT_OF_SCOPE 1, WRONG_PROVISION 1.

Counts on the 300 benchmark questions (dry run, no model): ANSWERABLE 113,
UNKNOWN 164, INSUFFICIENT_EVIDENCE 18, PARTIALLY_ANSWERABLE 4, OUT_OF_SCOPE 1.

## F. Decision logic

The gate is checked in this order; the first match decides:

1. **Scope** (from `analyze_question`). OUT_OF_SCOPE is PROVEN.
2. **Determination request**, by a conservative wording pattern. UNSUPPORTED_REQUEST is PROBABLE.
3. **Unidentified provision**: no CFR reference or docket, plus "paragraph (x)" or "this section". AMBIGUOUS is PROBABLE.
4. **Explicit provisions with none found**: INSUFFICIENT_EVIDENCE, PROVEN. The Stage 3 refusal text is kept.
5. **Nothing retrieved**: INSUFFICIENT_EVIDENCE, PROVEN. The existing no-context text is kept.
6. **Reference target only**: a citation lookup where *every* named provision follows a reference cue ("meeting", "refers to", "criteria of", "in accordance with", …). WRONG_PROVISION is PROBABLE.
7. **Requested value kind** (`regulus/rag/evidence_values.py`, shared with Stage 4 sufficiency). The kinds are temperature, date, duration/frequency, money, percentage, form number and count. The rule fires only when the question **asks** for the value ("what temperature range", "how often", "which FDA form"), not when it merely mentions the word.
   * If no retrieved source contains a value of that kind and the value is the whole question: INSUFFICIENT_EVIDENCE, PROVEN.
   * If the value is one clause of a multi-part question: PARTIALLY_ANSWERABLE.
8. **Coverage partial** or **mixed scope**: PARTIALLY_ANSWERABLE.
9. **No explicit provision**: UNKNOWN. **Otherwise**: ANSWERABLE.

No topic, number, provision or question-id rule exists; a test scans the gate
code for such literals.

The value test is by *kind*. The same question is answered when the evidence
contains a value of that kind (tested).

**Pre-adoption measurement** (retrieval only, 379 questions). The first
version of rule 7 would have blocked 11 questions:
- 2 false triggers ("time/temperature control", "in what form"), fixed by requiring an interrogative;
- 3 multi-part questions, now PARTIALLY_ANSWERABLE;
- 6 correct blocks.

A general "reference target" rule hit exactly the two citation lookups, so it
is restricted to citation lookups, and it blocks only when every named
provision is a target (S5-091, which names its container, is not blocked).

**Limits.**
- The value test cannot tell whether a source that contains *some* date
  contains *the* date asked for.
- UNKNOWN questions (the majority) are not judged before generation.
- The PROBABLE patterns can misfire. They fired only on the intended questions
  here, which is a small sample.

## G. Safe fallback design

One builder, `regulus/rag/fallback.py`, follows three rules:

* **Quote only what was asked.**
  * A replaced answer quotes the requested provision verbatim only when
    `quoting_allowed` holds: every requested provision is a section or
    paragraph with exact evidence, the question asks what it says
    (requirement / explanation / definition), and there are no focus terms and
    no requested value.
  * A part-level request, a citation lookup, or an applicability question gets
    **no quotation**.
  * For an exhaustive request, every material item is quoted.
  * Partial repairs never append verbatim text for part-level requests.
* **Say what the evidence does not establish.** Fallbacks say "the retrieved evidence does not establish…", never "the regulation does not contain…".
* **Never show an ungrounded repair.** If the final validation after repair is empty, degenerate, unsupported or evidence-mismatched, the text is replaced by the safe fallback: the verbatim provision when quoting is allowed, otherwise a withheld-answer message that lists the sources consulted, labels only.

Fallback types recorded:

| Type | Description |
|---|---|
| out_of_scope | out-of-scope decline |
| unsupported_request | determination request declined |
| ambiguous | provision not identified |
| wrong_provision | only the referenced provision was named |
| provision_not_found | no requested provision in the data |
| no_evidence | nothing retrieved |
| value_not_established | requested value absent; quotes the provision only when it is identified by section or paragraph |
| verbatim_requested_provision | repair quoted the requested provision (allowed) |
| unvalidated_answer_withheld | answer withheld; nothing quoted |

**Preserved text stages** (metadata and trace):
- `raw_model_output`, `repair_input`, `repair_output` (the repair's own text, kept even when a fallback replaces it), and the final answer;
- `answerability_state/reason/confidence/signals`, `generation_called`, `generation_blocked`, `block_reason`, `fallback_type` and `fallback_reason`.

Trace version: 2.

## H. Temperature incident before/after

Question UI-04: *"What exact storage temperature range does 21 CFR Part 211 require for all finished tablets?"*

**Stage 4** (`stage4_rediagnosed…/traces.jsonl`):

```text
evidence_sufficiency: EVIDENCE_INSUFFICIENT: the question asks for a temperature and no supplied source contains one
raw_model_output:     "21 CFR Part 211 requires that finished tablets be stored at a temperature range of 20°C to 25°C [1]. …"
repair_type:          extractive_replacement
final_answer:         "The generated answer could not be validated … The verified text of the requested provision(s) follows.
                       21 CFR part 211 (eCFR, binding, verbatim): (a) There shall be written procedures for production and process control …"
total:                18,598 ms
```

The Stage 4 system detected the insufficiency but acted on nothing. The model
invented 20–25 °C, and the fallback presented an unrelated passage as the
requested provision (F05 + F07 + F13 + F20).

**Stage 5** (`stage5_final_20260929T093254Z/traces.jsonl`):

```text
answerability_state:      INSUFFICIENT_EVIDENCE (PROVEN)
answerability_signals:    requested_value_kind=temperature, value_kind_in_evidence=false, sources=18,
                          requested_provisions=[21 CFR part 211], question_type=requirement, scope=in_scope
block_reason:             the question asks for a specific temperature or temperature range, and none of the 18 retrieved sources contains one
generation_called:        false        raw_model_output: null
fallback_type:            value_not_established
final_answer:             "The retrieved evidence does not establish the specific temperature or temperature range asked for: none of the
                           retrieved sources states one, so no specific temperature or temperature range is given. The regulation may address
                           the topic in general terms without stating one, or the relevant text may not have been retrieved.
                           Sources consulted: 21 CFR 211.100(a), 21 CFR 211.101, … and 13 more."
total:                    454 ms
```

This was fixed through the general value-kind mechanism; nothing about
temperature or Part 211 is special-cased. The same mechanism also resolves the
amount question (S5-051), the date question (S5-052) and the form-number
question (S5-050).

Remaining limitation: 21 CFR 211.142(b) ("appropriate conditions of
temperature") is not surfaced. That needs retrieval work on part-level
lookups, which was out of scope for this stage.

## P. Root causes not yet solved

* **Generation quality (12 of 19).** The 0.6B model omits requested elements,
  drops qualifiers and misattributes citations even when it has the exact
  evidence (F16 is confirmed by the controlled condition). The gate cannot help
  here: the evidence is sufficient.
* **General-knowledge questions (2 critical).** Nothing in the evidence proves
  they are unanswerable, so the gate does not block them. This was deliberately
  left for a later decision.
* **Referring-provision lookups (S5-090, S5-091).** Finding "which provision
  refers to X" needs retrieval by reference, not by identity. Retrieval was out
  of scope; the gate now declines safely instead of citing the wrong provision.
* **Part-level lookups (UI-04).** The relevant paragraph, 211.142(b), is not retrieved.
* **UNKNOWN general questions (14 diagnostic, 164 benchmark).** They are not judged before generation.
* **Value kinds.** Presence of *a* value of the kind is not proof of *the* value.
* **Three pre-existing slow-tier test failures.**
