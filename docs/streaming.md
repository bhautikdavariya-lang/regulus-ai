# Streaming answers (performance Stage 1)

The answering UI now shows the model's text as it is generated, then replaces
it with the validated answer. Answer content, retrieval, citations,
validation, repair, the model and its precision are unchanged. Baseline:
[performance_baseline.md](performance_baseline.md).

## Architecture

```
browser ── POST /api/ask/stream ──▶ serve_ui.py  (same lock, same Engine.ask, same pipeline)
                                      │
   {"type":"start"}               ◀───┤
   {"type":"context", sources}    ◀───┤ after retrieval + selection
   {"type":"generation_started"}  ◀───┤
   {"type":"delta", text} × n     ◀───┤ during the ONE model.generate() call (draft)
   {"type":"generation_finished"} ◀───┤
                                      │ validation → repair → citations (unchanged)
   {"type":"final", result}       ◀───┘ exactly what /api/ask returns, + "stream" stats
   or {"type":"error", error}
```

* **Transport:** newline-delimited JSON over a plain HTTP/1.0 response with
  no `Content-Length` (the body ends when the connection closes). It uses the
  standard library only, with no new dependency. `fetch` + `ReadableStream`
  reads it in the browser (EventSource cannot POST).
* **Text source:** `regulus/inference/streaming.py:TextCallbackStreamer`,
  transformers' own `TextStreamer` (word-boundary decoding, prompt and special
  tokens skipped) with the print replaced by a callback. It observes the
  existing `model.generate()` call. There is no second generation call, and
  greedy decoding is unchanged.
* **Plumbing:** `QwenGenerator.generate(..., on_text=None)` →
  `RagPipeline.answer(question, on_event=None)` → `Engine.ask(..., on_event=None)`.
  Every hook is optional and defaults to the previous behaviour; `/api/ask` is
  untouched.
* **Disconnects:** a failed socket write raises `ClientDisconnected` inside
  the streamer callback, which propagates out of `model.generate()`. Generation
  stops, the lock is released, and the server logs it. The page's **Stop**
  button aborts the fetch, which the server sees as a disconnect.
* **Errors:** an exception after headers are sent becomes one final
  `{"type":"error"}` event (sanitised, no paths or stack traces). A stream
  always ends with exactly one `final` or `error` event; the page treats a
  stream that closes without either as a failure, never as an answer.

## Draft vs. final

Validation and repair can replace or extend the model's text after
generation (invalid markers removed, extractive replacement, missing items
appended). So:

* delta text is shown in a dashed card labelled **"draft · generating"** with
  "not yet validated", and the status line moves to "validating the answer
  against its sources" when generation ends;
* the `final` event carries the validated answer, citations, sources and
  diagnostics, and the page renders it with the same `render()` as before,
  replacing the draft entirely;
* on error, the page shows the error and labels any text received as an
  "unvalidated draft".

A test streams an answer containing an invalid marker `[9]`: the draft shows
it, the final answer has it removed by the existing repair.

## Results

Live, on the configured system (Qwen3-0.6B, CPU float32, unchanged), measured
from the client with `python scripts/benchmark_streaming.py`
(`artifacts/latency/streaming_20260929T043722Z/`):

| Question | Tokens | Non-streaming: first byte = total | Streaming: first text | Streaming: final | Chunks | Final = non-streaming |
|---|---:|---:|---:|---:|---:|---|
| S5-001 single | 46 | 6.97 s | **2.19 s** | 5.44 s | 26 | yes |
| S5-012 section | 191 | 20.35 s | **2.97 s** | 19.25 s | 140 | yes |
| S5-024 multi | 487 | 40.92 s | **2.25 s** | 40.43 s | 354 | yes |
| S5-043 not found | 0 | 0.08 s | — (no model call) | 0.04 s | 0 | yes |
| S5-060 general | 104 | 10.74 s | **2.29 s** | 9.81 s | 68 | yes |
| S5-070 guidance | 202 | 18.14 s | **2.60 s** | 18.25 s | 148 | yes |
| S5-100 long | 216 | 17.46 s | **2.01 s** | 17.47 s | 118 | yes |

* Time to first visible text: median **2.27 s** (was the whole answer, median
  17.5 s on this set). First text always arrived before the answer completed.
* The first byte (the `start` event) arrives in about 1 ms, and sources are
  listed as soon as retrieval ends.
* Overhead: with the order reversed so neither side benefits from warm-up,
  streaming totals were −10 to +350 ms (≤ 2 %) and generation 28–266 ms longer,
  within run-to-run noise. `TextStreamer` re-decodes the current line's tokens
  on every step, which is the only plausible real cost.
* Non-streaming path: three recorded answers regenerated byte-identical
  (`artifacts/answer_shape/streaming_stage_check_*`).

## Tests

* `tests/test_streaming.py`: the streamer on the real Qwen tokenizer (chunks
  add up to the decoded text; a failing callback stops it); pipeline events,
  multiple chunks, completion, generation error, empty answer, cancellation,
  validation still running (and repairing), citations and validation
  identical to the non-streaming path, no change without a listener; HTTP:
  event order and exactly one final, final = `/api/ask` response, error event,
  empty question 400, real socket disconnect stopping generation and freeing
  the lock.
* `tests/test_streaming_ui.py` + `tests/answer_ui_stream_harness.js`: the
  page's own script under Node with events split mid-line across network
  reads: draft shown then replaced, error with draft, stream closing without a
  final event.

## Limitations and risks

* **The draft can differ from the answer**, by design. A user who reads the
  draft carefully may see text that repair later removes or replaces.
  The labelling says so; nothing hides the change.
* **Word-level chunks.** `TextStreamer` holds back a partial word; text
  appears word by word, not token by token.
* **One request at a time** (the existing lock): a second browser tab waits
  for the first answer, now visibly (it gets `start` immediately, then nothing
  until the lock frees).
* **Disconnect is detected on the next write.** During retrieval and prefill
  (about 2 s) nothing is written, so a disconnect there is noticed at the
  first draft chunk.
* **Browser rendering was tested under Node, not in a real browser.** The page
  re-renders the draft card on every chunk (about 350 times for a long
  answer); cheap at this size, but not measured in a browser.
* No proxy is involved locally. Behind a buffering proxy the stream would need
  that proxy's buffering disabled (`X-Accel-Buffering: no` is already sent).
